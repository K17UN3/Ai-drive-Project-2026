## 2. テストケース詳細

### TST-CHAT-001：2タブ間の双方向送受信・重複なし描画・DB 1行保存
* **対応REQ / DES:** `REQ-CHAT-001`, `REQ-CHAT-003`, `REQ-CHAT-004` / `DES-CHAT-002`, `DES-CHAT-003`, `DES-CHAT-004`
* **前提とデータ:**
  * サーバーが起動しており、`chat_seats` および `chat_messages` が空の状態（参加人数 0人）。
  * ブラウザで `http://localhost:3000/chat` を2つのタブ（**タブA**・**タブB**）で開き、ともに `Room 1`（`2 / 5 人`）へ入室済みであること。
* **操作:**
  1. **タブA** でユーザー名 `Alice`、コメント `こんにちは、タブAです` を入力して送信する。
  2. 2秒待機し、**タブA** と **タブB** の画面表示を確認する。
  3. 続いて **タブB** でユーザー名 `Bob`、コメント `返信です、タブBより` を入力して送信する。
  4. 2秒待機し、**タブA** と **タブB** の画面表示および DB のレコードを確認する。
* **期待結果:**
  * 操作1〜2の直後、**タブA（送信側）** のメッセージ一覧に `Alice` の投稿が **1件だけ** 表示され、二重表示されないこと。
  * **タブB（受信側）** にもページリロードなしで `Alice` の投稿が **1件だけ** 追加表示されること。
  * 操作3〜4の直後、**タブB** および **タブA** の双方に `Bob` の投稿が時系列順で **1件だけ** 追加表示されること。
  * DB の `chat_messages` テーブルに、上記2件のメッセージがそれぞれ **1行ずつ（計2行）** だけ保存されていること。
* **確認場所:**
  * **画面:** タブA・タブBのメッセージ一覧表示エリア（表示件数・重複の有無・表示順）。
  * **ログ:** サーバーターミナル（`POST /api/chat/messages` が各1回 `201` で処理されていること）。
  * **DB:** `SELECT id, room_id, user_name, comment, created_at FROM chat_messages WHERE room_id = 1 ORDER BY id ASC;`

### TST-CHAT-002：21件以上の履歴からの最新20件昇順表示・取得と新着の重複排除
* **対応REQ / DES:** `REQ-CHAT-004`, `REQ-CHAT-005` / `DES-CHAT-003`, `DES-CHAT-004`
* **前提とデータ:**
  * `Room 1` に連番のメッセージが **25件**（例: `msg-01` 〜 `msg-25`、ID 1〜25）保存されている状態。
  * テスト後半用に、さらに連続投稿して DB 上の保持上限（50件）も確認できるようにする。
* **操作:**
  1. 新規タブ（**タブC**）で `/chat` にアクセスし、`Room 1` へ入室する。
  2. 画面に表示されたメッセージ件数と並び順を確認する。
  3. 開発者ツール（Network スロットリングを `Slow 3G` に設定）で初期入室（`POST /api/chat/join`）を実行すると同時に、別タブ（**タブA**）から `msg-26` を投稿し、履歴取得応答と初回ポーリング（`GET /api/chat/sync`）が交差する状況を作る。
  4. さらに合計 **55件** になるまでメッセージを投稿し、DB の総レコード数を確認する。
* **期待結果:**
  * 操作2で、古い5件（`msg-01` 〜 `msg-05`）は表示されず、**最新の20件（`msg-06` 〜 `msg-25`）** が上から古い順（`msg-06` が一番上、`msg-25` が一番下）に表示されること。
  * 操作3で、履歴取得と新着同期が重なっても `msg-26` は画面上に **1件だけ** 表示され、重複描画されないこと。
  * 操作4で、DB の `chat_messages` テーブルの `room_id = 1` のレコード数が **最大50件（`msg-06` 〜 `msg-55`）** に維持され、51件目以降が溢れないこと。
* **確認場所:**
  * **画面:** タブCのメッセージ一覧の先頭要素・末尾要素・総DOM要素数。
  * **ログ:** ブラウザ DevTools Network（`join` と `sync` のレスポンス内容）。
  * **DB:** `SELECT COUNT(*) FROM chat_messages WHERE room_id = 1;`（50件以下であること）および `SELECT MIN(id), MAX(id) FROM chat_messages WHERE room_id = 1;`

### TST-CHAT-003：複数ルーム間での履歴・新着の非公開分離
* **対応REQ / DES:** `REQ-CHAT-001`, `REQ-CHAT-003`, `REQ-CHAT-005` / `DES-CHAT-002`, `DES-CHAT-003`
* **前提とデータ:**
  * `Room 1` にすでに5タブ接続済み（`5 / 5 人`）で、`Room 1` にメッセージ `Room1専用メッセージ` が投稿済みである状態。
  * `Room 2` は現在 0人（空きあり）である状態。
* **操作:**
  1. 6つ目のタブ（**タブ6**）で `/chat` にアクセスする。
  2. **タブ6** の割り当てルーム表示と初期メッセージ一覧を確認する。
  3. **Room 1** に参加中のタブ（**タブ1**）から新規メッセージ `Room1の新着` を送信する。
  4. 3秒待機し、**タブ6（Room 2）** の画面および API レスポンスを確認する。
  5. **タブ6（Room 2）** から `Room2の投稿` を送信し、**タブ1（Room 1）** の画面を確認する。
* **期待結果:**
  * 操作1〜2で、**タブ6** は `Room 2`（`1 / 5 人`）に割り当てられ、`Room 1` の履歴（`Room1専用メッセージ`）が **一切表示されない** こと。
  * 操作3〜4で、**タブ6（Room 2）** の画面に `Room1の新着` が表示されず、`GET /api/chat/sync` のレスポンス `messages` にも含まれないこと。
  * 操作5で、**タブ1（Room 1）** の画面に `Room2の投稿` が表示されないこと。
* **確認場所:**
  * **画面:** タブ1（Room 1）とタブ6（Room 2）のルーム名表示・メッセージ一覧表示。
  * **ログ:** ブラウザ DevTools Network（タブ6の `join` および `sync` の JSON レスポンス）。
  * **DB:** `SELECT id, room_id, comment FROM chat_messages ORDER BY id DESC LIMIT 10;`

### TST-CHAT-004：5接続入室・6接続目（全室満席時）の制限と空席時の自動再試行入室
* **対応REQ / DES:** `REQ-CHAT-006`, `REQ-CHAT-007` / `DES-CHAT-002`, `DES-CHAT-004`, `DES-CHAT-005`
* **前提とデータ:**
  * ルーム定員は1室5名（全3室で合計15名）。
  * 検証効率化のため、1ルームの満席挙動（5人入室→6人目が別室へ）および全3室満席挙動（15人入室→16人目が満席待機）の双方を検証可能な状態にする。
* **操作:**
  1. ブラウザのタブを1つずつ開き、**1〜5タブ目** の割り当てルームを確認する。
  2. **6タブ目** を開き、割り当てルームを確認する。
  3. 続けて **7〜15タブ目** を開き、全3ルームが `5 / 5 人`（計15接続）になった状態を作る。
  4. **16タブ目** で `/chat` にアクセスする。
  5. **16タブ目** の画面表示を確認し、ブラウザ DevTools コンソールから直接 `fetch('/api/chat/sync?afterId=0')` および `fetch('/api/chat/messages', { method: 'POST', ... })` を実行する。
  6. 1〜15タブ目のうち **1つのタブを閉じる**。
  7. **16タブ目** を操作せずに最大5秒待機し、画面の変化を確認する。
* **期待結果:**
  * 操作1〜2で、1〜5タブ目が `Room 1` に入り、**6タブ目は `Room 1` に入室できず `Room 2` へ割り当てられる**こと。
  * 操作3〜4で、11〜15タブ目が `Room 3` に入り、**16タブ目は「満席待機画面」が表示される**こと。
  * 操作5で、16タブ目には過去の会話履歴・新着メッセージ・投稿フォームが表示されず、直接 API を叩いても `401 Unauthorized`（`SEAT_EXPIRED`）となり **閲覧・受信・投稿のいずれも利用できない** こと。
  * 操作6〜7で、1席空いたことをクライアントの自動ポーリングが検知し、**手動リロードなしで16タブ目が自動的に入室状態へ切り替わり最新20件が表示される**こと。
* **確認場所:**
  * **画面:** 1〜15タブ目のヘッダ人数表示（`5 / 5 人`）、16タブ目の満席待機表示および空席発生後の自動遷移画面。
  * **ログ:** ブラウザ DevTools Network（16タブ目の `POST /api/chat/join` の定期ポーリングと `joined: false` → `joined: true` への変化）。
  * **DB:** `SELECT room_id, COUNT(*) FROM chat_seats GROUP BY room_id ORDER BY room_id;`（各ルーム最大5件以下であること）。

### TST-CHAT-005：切断中の送信不可・切断中投稿の再入室反映・接続反復後の重複なし表示
* **対応REQ / DES:** `REQ-CHAT-005`, `REQ-CHAT-007`, `REQ-CHAT-010` / `DES-CHAT-004`, `DES-CHAT-005`
* **前提とデータ:**
  * `Room 1` に **タブA** と **タブB** が入室している状態。
* **操作:**
  1. **タブB** のブラウザ DevTools（Network タブ）を `Offline` に切り替える（通信切断状態）。
  2. **タブB** でコメント `切断中の送信テスト` を入力し、送信ボタンを押下する。
  3. **タブB** が `Offline` のまま **50秒間** 待機する（サーバー側の45秒タイムアウトによる席回収を発生させる）。
  4. その間に **タブA** から `切断中に投稿されたメッセージ1` と `切断中に投稿されたメッセージ2` を送信する。
  5. **タブB** の DevTools を `No throttling`（オンライン復帰）に戻す。
  6. **タブB** が自動再入室（`401` 検知 → `POST /api/chat/join`）した後の画面表示を確認する。
  7. さらに **タブB** で `Offline` → `Online` の切り替えを **3回反復** し、その後 **タブA** から `反復後の新規メッセージ` を送信する。
* **期待結果:**
  * 操作2で、切断中は送信が失敗し、画面に通信エラー案内が表示され、**送信は完了しない**（DBにも保存されない）こと。
  * 操作5〜6で、オンライン復帰後に自動再入室が行われ、切断中にタブAが投稿した **2件のメッセージが漏れなく履歴に反映される** こと。
  * 操作7で、接続の切断・再入室を3回反復した後でもタイマーやイベントリスナーが多重化せず、`反復後の新規メッセージ` が **1件だけ** 表示されること。
* **確認場所:**
  * **画面:** タブBのエラー通知表示、再入室後のメッセージ一覧（件数・重複なし）。
  * **ログ:** ブラウザ DevTools Network（`401 SEAT_EXPIRED` → `POST /api/chat/join` → `GET /api/chat/sync` が1系列のみで動作していること）。
  * **DB:** `SELECT seat_token, room_id, last_seen_at FROM chat_seats;`（古い失効席が回収され、有効席のみ残っていること）。

### TST-CHAT-006：入力検証（空文字・空白のみ・型不正・境界値・絵文字・改行・XSSエスケープ）
* **対応REQ / DES:** `REQ-CHAT-002`, `REQ-CHAT-009` / `DES-CHAT-006`
* **前提とデータ:**
  * `Room 1` に入室済みのブラウザタブ、および API 直接検証用の DevTools コンソール。
* **操作:**
  1. **空文字・空白のみ:** ユーザー名またはコメントを空文字 `""`、半角スペースのみ `"   "`、全角スペースのみ `"　　　"` にして送信する。
  2. **型の不正（サーバー検証）:** DevTools コンソールから `fetch('/api/chat/messages', { method: 'POST', headers: { 'Content-Type': 'application/json', 'x-seat-token': '<有効トークン>' }, body: JSON.stringify({ userName: 12345, comment: ['array'] }) })` を送信する。
  3. **上限ちょうど（境界値内）:**
     * ユーザー名 **20文字**（例: `あいうえおかきくけこさしすせそたちつてと`）
     * コメント **500文字**（500文字の文字列）を入力して送信する。
  4. **上限超過（境界値外）:**
     * ユーザー名 **21文字**（前後空白除去後）
     * コメント **501文字**（前後空白除去後）を入力して送信する。
  5. **絵文字・連続改行:**
     * ユーザー名に絵文字 `太郎😀` を入力して送信する。
     * ユーザー名 `太郎`、コメントに `1行目\n\n\n2行目`（3連続改行）を入力して送信する。
  6. **タグ風文字列（XSS対策）:**
     * ユーザー名 `<b>太字テスト</b>`、コメント `<script>alert('XSS')</script><img src=x onerror=alert(1)>` を入力して送信する。
* **期待結果:**
  * 操作1：クライアント／サーバー双方で拒否され、エラー案内が表示され、DBに保存されないこと。
  * 操作2：サーバーが `400 Bad Request`（`INVALID_INPUT`）を返し、サーバーがクラッシュしないこと。
  * 操作3（上限ちょうど）：20文字のユーザー名・500文字のコメントがともに正常に保存・表示されること。
  * 操作4（上限超過）：エラー案内が表示され、保存・配信されないこと。
  * 操作5：絵文字入りユーザー名はエラーで拒否されること。連続改行は自動的に **1回の改行（`1行目\n2行目`）** に正規化されて保存・表示されること。
  * 操作6：アラートダイアログの実行や太字装飾は一切発生せず、`<script>alert('XSS')</script>...` が **そのままのテキスト文字列** として画面に表示されること。
* **確認場所:**
  * **画面:** バリデーションエラーメッセージ、描画されたDOM要素（DevTools Elements でテキストノードとしてエスケープされていること）。
  * **ログ:** ブラウザ DevTools Network（`400` 応答ボディ）。
  * **DB:** `SELECT user_name, comment FROM chat_messages ORDER BY id DESC LIMIT 5;`

### TST-CHAT-007：検証用DBでの保存・履歴取得失敗、通信失敗案内、保存失敗時の非配信
* **対応REQ / DES:** `REQ-CHAT-009`, `REQ-CHAT-010` / `DES-CHAT-003`, `DES-CHAT-006`
* **前提とデータ:**
  * 検証用ローカル環境（`.env` を一時変更可能な状態）。
  * `Room 1` に **タブA** と **タブB** が入室している状態。
* **操作:**
  1. **保存失敗時の非配信確認:**
     * 検証用 DB で一時的に `chat_messages` への書き込みエラーを発生させる（例: 検証用DBで `ALTER TABLE chat_messages RENAME TO chat_messages_bak;` または `.env` の DB接続先を一時的に不正値にして再起動）。
     * **タブA** からメッセージ `保存失敗テスト` を送信する。
     * **タブA** の画面・入力欄の状態、および **タブB** の画面を確認する。
  2. **履歴取得失敗時の確認:**
     * 上記 DB 障害状態のまま、新規タブ（**タブC**）で `/chat` を開く（`POST /api/chat/join` 内のDBアクセスが失敗する状態）。
  3. **復旧確認:**
     * テーブル名（または `.env`）を元に戻し、エラー案内が消えて正常動作へ復帰することを確認する。
* **期待結果:**
  * 操作1：サーバープロセスがダウンせず `500 INTERNAL_ERROR` を返却し、**タブA** の画面に安全なエラー案内（「サーバーでエラーが発生しました」等）が表示され、入力欄のテキストが保持されること。また、**保存に失敗したメッセージがタブB（他ユーザー）へ配信されない**こと。
  * 操作2：**タブC** に DB 接続情報（`DATABASE_URL` や SQL エラー詳細）が露出せず、安全なエラー案内が表示されること。
  * 操作3：DB復旧後、特別なサーバー再起動なし（DBテーブル復旧の場合）で正常にメッセージ送受信が再開できること。
* **確認場所:**
  * **画面:** タブA・タブB・タブCのエラーメッセージ表示（秘密情報やスタックトレースが含まれないこと）。
  * **ログ:** サーバーターミナル（`[Chat Error]:` として詳細エラーが記録されていること）。
  * **DB:** 復旧後に `chat_messages` へ不完全なデータが残っていないこと。

### TST-CHAT-008：複数インスタンス間の同期・同時入室による5席目排他制御
* **対応REQ / DES:** `REQ-CHAT-008` / `DES-CHAT-005`
* **前提とデータ:**
  * 同一の検証用 Neon DB を参照する **2つのサーバーインスタンス** を起動する（ローカル検証：`PORT=3001 npm run dev` と `PORT=3002 npm run dev`、または Vercel 上の複数インスタンス）。
  * 初期状態では `chat_seats` が空（0接続）であること。
* **操作:**
  1. **インスタンス間双方向同期:**
     * ブラウザ1で **インスタンスA（`http://localhost:3001/chat`）** に接続（`Room 1` 入室）。
     * ブラウザ2で **インスタンスB（`http://localhost:3002/chat`）** に接続（`Room 1` 入室）。
