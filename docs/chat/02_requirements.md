# チャット機能 要件定義書

* **文書ファイル:** `docs/chat/02_requirements.md`
* **ステータス:** 確定版（仕様確認反映済み）
* **対象システム:** 既存Webアプリケーション（授業用アプリ）

---

## 1. 概要・位置づけ

### 1.1 目的
複数ユーザー間でリアルタイムにテキストメッセージをやり取りできる簡易チャット機能を新規追加し、既存アプリケーションにおけるリアルタイム通信および複数インスタンス間での状態同期・排他制御の学習・実践基盤を提供する。

### 1.2 利用者
* 既存Webアプリケーションにアクセス可能な一般利用者（授業参加者・検証者）。
* ログイン認証は不要とし、入室時に任意のユーザー名を入力して利用する。

### 1.3 対象範囲（スコープ内）
* `/chat` ルートにおけるチャット画面の提供。
* 全3ルーム（各ルーム定員5名、全体最大15名）の自動割り振りおよび定員超過時の待機・自動入室制御。
* ユーザー名とコメントのバリデーション（文字数、絵文字制限、改行制限、前後空白処理）および同一ルーム内へのリアルタイム配信。
* 既存RDB（リレーショナルデータベース）を用いたメッセージの永続化（1ルーム最大50件保持）および複数インスタンス間の同期・参加人数管理。
* 初期表示および再接続時の過去ログ（最新20件）の取得・表示。

### 1.4 対象外（スコープ外）
* ユーザー登録・ログイン認証機能、およびユーザーごとのアカウント管理。
* 投稿済みメッセージの編集・削除機能、画像・ファイル添付機能、リアクション（スタンプ等）機能。
* 21件目以前の過去ログを遡って閲覧するページネーション・無限スクロール機能。
* ユーザーによる任意の新規ルーム作成・削除機能、およびルーム指定での入室機能。

### 1.5 既存機能との関係
* 既存のルーティング構成（TOP、TODO、AI質問、404ページ、共通エラーハンドリング）と独立した `/chat` プレフィックス配下に機能を追加する。
* 既存画面（TOP等）へのナビゲーションリンク追加は行わず、URL直接アクセス（例: `http://localhost:xxxx/chat`）を入口とする。
* 既存DBインスタンスを共有し、既存のテーブル構造や既存機能の動作に影響を与えない独立したテーブル設計とする。

## 3. 画面・振る舞い仕様

### 3.1 ルーム構成と初期表示（`/chat`）
* **ルーム構成:** システム内に固定で3つのルーム（`room-1`, `room-2`, `room-3`）を用意する。
* **入室割り振りルール:**
  1. ユーザーが `/chat` にアクセスすると、サーバーは `room-1` → `room-2` → `room-3` の順（または空きがあるルーム）を確認し、現在参加数が5名未満のルームへ接続を割り当てる。
  2. 参加人数は**接続単位（WebSocket / SSE / ポーリングセッション等のコネクション単位）**でカウントする。同一人物が複数タブ・複数ブラウザで開いた場合は別々の参加者として扱う。
  3. 画面上部またはヘッダー付近に、現在割り当てられているルーム名（例: `Room 1`）と現在の参加人数（例: `3 / 5 人`）を表示する。
  4. 割り当てられたルームの最新メッセージ最大20件をRDBから取得し、時系列順（上が古く、下が新しい）に描画する。

### 3.2 ユーザー名とコメントの入力・送信
* **ユーザー名入力:**
  * 入力必須。前後の半角・全角スペースは送信前にトリミング（除去）する。
  * トリミング後の文字数が **1文字以上20文字以内** であること。
  * **絵文字（Unicode Emoji）の使用は禁止**とする。絵文字が含まれる場合は送信を拒否し、エラーメッセージを表示する。
  * 1度送信したユーザー名は、同一画面（タブ）内での再入力の手間を省くため入力欄に保持される。
* **コメント入力:**
  * 入力必須。前後の半角・全角スペースおよび前後の改行はトリミングする。
  * トリミング後の文字数が **1文字以上500文字以内** であること。
  * 改行は許可するが、**連続する改行は最大1行（改行コード1つ分、空行を作らない形式）**に制限する（例: `\n\n` 以上が入力された場合は `\n` 1つに正規化するか、バリデーションエラーとする）。

### 3.3 同じルームへの配信とDB保存
* バリデーションを通過したメッセージは、現在入室中のルームID・ユーザー名・コメント本文・投稿タイムスタンプとともに既存RDBへ保存される。
* 保存処理と同時に、同一ルームの総レコード数を確認し、50件を超過している場合は作成日時が古いレコードから順に削除して**最大50件**を維持する。
* 同じルームに接続している全クライアントの画面へリアルタイムに配信され、各クライアントのメッセージ一覧の末尾に追記される。画面上の表示件数が20件を超えた場合、古い表示要素をDOMから削除するかスクロール領域内で維持する。

### 3.4 初期表示と再接続での最新20件表示
* ブラウザのリロードやネットワーク瞬断からの再接続時は、現在の表示リストを一度クリアしたうえで、サーバー（RDB）から該当ルームの最新20件を再取得して描画する。これにより、切断中に他者が投稿したメッセージの取りこぼしを防ぐ。

### 3.5 満席時の画面表示と制限（全3ルーム満席・16人目以降）
* 全3ルームがすべて5名ずつ埋まっている状態（合計15接続）で新たな接続リクエストが来た場合、入室を拒否し、通常のチャット画面とは異なる**「満席待機画面」**を表示する。
* **満席待機画面での制限事項:**
  * **入室制限:** いずれのルームにも所属しない状態とする。
  * **閲覧制限:** 過去のメッセージ履歴およびリアルタイムに投稿されているメッセージ内容は一切表示・送信しない（APIレスポンスにも含めない）。
  * **投稿制限:** ユーザー名・コメントの入力フォームおよび送信APIへのアクセスを無効化する。
* **自動ポーリングによる再試行:**
  * 満席待機画面では、クライアント側から一定間隔（例: 3〜5秒ごと）でサーバーへ空き状況を確認する自動ポーリングを実行する。
  * いずれかのルームに空き（5名未満）が発生したことを検知した時点で、自動的に入室処理を実行し、チャット画面（最新20件表示）へ切り替える。

## 4. 入力検証・例外処理・セキュリティ・回帰要件

### 4.1 入力値検証（バリデーション）および異常データ処理
| 項目 | 検証ルール・処理仕様 |
| :--- | :--- |
| **入力の型** | ユーザー名・コメントともに文字列型（String）のみを受け付ける。JSONの不正な型（数値・配列・オブジェクト・null）が送信された場合は HTTP `400 Bad Request` を返却し処理を中断する。 |
| **前後空白** | ユーザー名・コメントともに、先頭および末尾の半角スペース・全角スペース・タブ文字を除去（`trim`）した後の値で必須チェック・文字数チェックを行う。空白のみの入力は空文字とみなしエラーとする。 |
| **文字数超過** | ユーザー名21文字以上、コメント501文字以上のリクエストはクライアント側・サーバー側双方で検証し、サーバー側で超過を検知した場合は保存・配信を行わずエラーを返却する。 |
| **絵文字・改行制限** | ユーザー名に絵文字が含まれる場合はエラーとする。コメントの連続改行（2回以上連続する改行）は1回の改行へ正規化またはエラーとして扱う。 |

### 4.2 通信失敗・DB障害時の振る舞い
* **通信失敗（ネットワーク切断・タイムアウト）:**
  * メッセージ送信時に通信が失敗した場合、送信失敗のエラー通知を画面に表示し、入力中のテキストは消去せず保持する。
  * サーバーとのリアルタイム接続が切れた場合、画面上に「再接続中...」等のステータスを表示し、自動再接続を試みる。
* **DB障害（接続エラー・クエリタイムアウト・ロック競合）:**
  * DBへの読み書きに失敗した場合、サーバーは例外を捕捉して HTTP `500 Internal Server Error`（または適切なエラーレスポンス）を返却し、プロセス全体をダウンさせない。
  * クライアント側には「現在サーバーが混み合っているか、一時的な障害が発生しています」等の安全なエラーメッセージを表示する。

### 4.3 セキュリティ要件
* **XSS（クロスサイトスクリプティング）対策:**
  * ユーザー名およびコメントを表示する際は、HTML特殊文字（`<`, `>`, `&`, `"`, `'`）を必ずエスケープ処理し、`innerHTML` 等による生HTMLの挿入を行わない。
* **秘密情報の管理:**
  * DB接続文字列、APIキー、セッションシークレット等の機密情報は環境変数（`.env` 等、Git管理対象外）で管理し、フロントエンドへ配信されるバンドルファイルやHTMLソース、エラーレスポンスのスタックトレースに絶対に含めない。

### 4.4 既存機能の回帰確認（リグレッションテスト項目）
チャット機能の実装・デプロイ後、以下の既存機能が影響を受けていないことを確認する。
1. **TOP画面（`/`）:** 正常に表示され、既存のコンテンツやリンクが動作すること。
2. **TODO機能:** タスクの追加・一覧表示・完了切替・削除が既存DB上で正常に動作すること。
3. **AI質問機能:** 質問の送信から回答の取得・表示まで一連のフローが正常に動作すること。
4. **404エラー処理:** 存在しないURL（例: `/unknown-page`）へアクセスした際、既存の404ページが正しく表示されること。
5. **共通エラー処理:** 既存機能で意図的にエラーを発生させた際、既存のエラーハンドリング（エラー画面表示やログ出力）が正常に機能すること。

## 5. 複数インスタンス同期および定員制御の条件

本システムは Redis 等の外部インメモリDBを追加せず、**既存のRDB（リレーショナルデータベース）のみを共有基盤**として複数アプリケーションインスタンス間の同期と人数制御を実現する。

### 5.1 既存RDBを用いた設計方針
* **メッセージ同期:**
  * 投稿されたメッセージをRDBの `chat_messages` テーブルへ `INSERT` する。
  * 各インスタンス（または各クライアント）は、RDBのポーリング（例: 1秒間隔での差分取得 `WHERE id > last_seen_id`）またはDBの通知機能（PostgreSQLの `LISTEN/NOTIFY` 等、利用中のRDBがサポートする機構）を用いて新規メッセージを検知し、自インスタンスに接続中のクライアントへ配信する。
* **全インスタンス合計で「1ルーム5人」を守る排他制御条件:**
  * RDB上にアクティブな接続を管理する `chat_connections` テーブル（カラム例: `connection_id`, `room_id`, `instance_id`, `last_heartbeat_at`）を設ける。
  * **入室時の排他制御:** 入室処理は必ず**DBトランザクションおよび行ロック（`SELECT ... FOR UPDATE` またはルーム管理テーブルのロック）**内で実行する。トランザクション内で該当ルームの有効接続数（`last_heartbeat_at` が現在時刻からタイムアウト秒数以内のレコード数）をカウントし、5件未満であることを確認した上でのみ新規レコードを `INSERT` してコミットする。これにより、複数インスタンスへ同時に6人目・16人目がアクセスした場合でも、競合状態（Race Condition）による定員超過を確実に防止する。
  * **死活監視と枠解放:** 各接続は定期的（例: 15秒ごと）に `last_heartbeat_at` を更新する。ブラウザ終了時の切断イベント受信時は即座に該当レコードを `DELETE` し、異常切断時は `last_heartbeat_at` が **30秒〜60秒** 経過したレコードを無効（離脱済み）とみなしてカウント対象から除外・削除する。

### 5.2 環境別の検証条件

#### A. ローカル環境での確認条件（単一インスタンス・複数プロセス検証）
1. **基本機能・バリデーション確認:**
   * ローカルでアプリサーバーを1プロセス起動し、`/chat` へアクセスしてルーム割り振り、文字数・絵文字・改行制限、XSSエスケープが仕様通り動作することを確認する。
2. **定員制御・満席ポーリング・離脱解放の確認:**
   * 同一PCからブラウザのタブ（またはシークレットウィンドウ）を順次16個開き、1〜5タブ目が `Room 1`、6〜10タブ目が `Room 2`、11〜15タブ目が `Room 3` に割り当てられることを確認する。
   * 16タブ目で「満席待機画面」が表示され、メッセージ閲覧・投稿ができないことを確認する。
   * 1〜15タブ目のうち1つを閉じた後、16タブ目が自動ポーリングにより数秒以内に自動入室し、最新20件が表示されることを確認する。
   * ネットワーク遮断等によりHeartbeatを停止させ、30秒〜60秒経過後に枠が解放されることを確認する。
3. **擬似複数インスタンス確認（ローカルマルチポート）:**
   * 同一のローカルRDBを参照する状態で、ポート番号を変えた2つのサーバープロセス（例: `PORT=3001` と `PORT=3002`）を起動し、後述の「複数台確認条件」と同等の同期・同時入室テストを実施する。

#### B. 複数台（複数インスタンス）環境での確認条件
1. **インスタンス間メッセージ同期:**
   * ロードバランサー配下のインスタンスA（`1〜5人目` の一部）とインスタンスB（同じルームの別ユーザー）に接続した状態で、インスタンスA側から投稿したメッセージが、1〜2秒以内にインスタンスB側の画面へ反映されること。
2. **同時アクセス時の定員厳守（競合テスト）:**
   * 残り空き枠が「あと1枠（14/15人接続中）」の状態で、インスタンスAとインスタンスBそれぞれに対して同時に新規入室リクエストを送信した際、**どちらか一方のみが入室成功（15/15人）となり、もう一方が確実に満席待機画面へ誘導されること**（合計16人にならないこと）。
3. **片系インスタンス停止時のリカバリ:**
   * インスタンスAを強制停止した際、インスタンスAに接続していたユーザーの枠がタイムアウト（30秒〜60秒）後に解放され、インスタンスB経由で新規ユーザーが空き枠に入室できること。
