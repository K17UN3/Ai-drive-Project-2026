# AI質問アプリV2 要件定義書

## 1. プロジェクト概要・目的

### 1.1 目的
本プロジェクト（AI質問アプリV2）は、V1で実現した「単発のAI質問・回答およびログ閲覧機能」を拡張し、**「話題ごとに独立した会話スレッドを作成・切り替え、過去の文脈を踏まえた連続対話（マルチターン対話）を行えるWebアプリケーション」**を提供することを目的とする。

### 1.2 利用者（ターゲットユーザー）
* **一般利用者（受講者・アプリユーザー）**: 学習や業務の調査において、1つのテーマを深掘りしたり、話題ごとにスレッドを分けてAIに質問したりする利用者。
* **システム管理者・開発者**: アプリケーションのデプロイ・環境変数設定（APIキー管理）・DB運用および授業課題の評価を行う担当者。

### 1.3 開始条件（前提条件）
* V1のバックエンド基盤（Express / TypeScript）、PostgreSQLデータベース接続（`db.ts`）、および Gemini API 連携環境が稼働していること。
* 環境変数 `GEMINI_API_KEY` がサーバー環境に正しく設定されていること。
* 既存のTOPページ（`/`）およびTODOアプリ（`/todo`）が正常に動作していること。

## 2. 対象範囲（スコープ）と区分

### 2.1 対象範囲（In-Scope / Out-of-Scope）
* **対象内（In-Scope）**:
  * 会話スレッド（Conversation）の新規作成・一覧取得・選択切り替え機能
  * 選択中の会話スレッド内での連続質問送信（直近5往復分の文脈付与）およびDB永続化
  * 会話スレッド内の履歴表示（最大20往復表示）および再読み込み後の状態復元
  * V1既存機能（TOP、TODO、V1 API/画面）の非破壊維持および環境変数未設定時の安全な機能停止
* **対象外（Out-of-Scope）**:
  * ユーザー認証・ログイン機能（単一ブラウザ/共有環境または匿名セッションベースでのスレッド管理を前提とする）
  * 画像・音声・ファイルアップロードによるマルチモーダル質問
  * 会話履歴のCSV/PDFエクスポート機能、およびメッセージ単位の個別編集・削除

### 2.2 必須要件と発展要件の区分
| 区分 | 対象内容 | 位置づけ |
| :--- | :--- | :--- |
| **必須要件 (Must)** | 会話スレッド作成・切替・一覧表示、文脈継続（5往復送信）、履歴表示（20往復）、再読み込み復元、エラー制御、V1非干渉、公開時停止ガード | 授業時間内に完了し、受入条件を100%満たすべき基本要件 |
| **発展要件 (Want)** | 会話タイトルのAI自動要約生成、会話スレッドの削除・名称変更機能、検索フィルタリング | 必須要件完了後に着手する拡張要件（本書の未決・拡張項目として定義） |

## 4. 機能要件（必須要件）

### REQ-V2-01: 同じ会話での文脈継続（Geminiへの直近5往復送信）
* **対応WISH**: `WISH-V2-01`
* **根拠**: 利用者が直前の質問・回答を踏まえた指示（「それをもっと詳しく」「具体例を挙げて」等）を行えるようにするため。また、トークン上限超過や応答遅延を防ぐため、AIへ送信する文脈を適切に制限する必要があるため。
* **要件内容**:
  * 選択中の会話スレッド内で追加質問を送信する際、当該会話に紐づく過去のメッセージ履歴から**直近最大5往復（質問5件＋回答5件＝最大10メッセージ）**を時系列順（古い順）に抽出し、今回の新規質問と結合して Gemini API へ送信する。
  * 画面表示用の履歴件数（最大20往復）と、Gemini API へ渡す文脈件数（最大5往復）を明確に分離して制御する。
* **受入条件（操作判定）**:
  1. 同一会話内で「日本の首都は？」と送信して「東京」の回答を得た後、「そこの人口は？」と追加送信した際、東京の人口に関する回答が返ること。
  2. 同一会話内で7往復以上のやり取りを行った後、8回目の質問を送信した際、APIリクエストには直近5往復分の文脈のみが含まれ、1〜2往復目の古い文脈は送信されないこと（サーバーログまたはネットワーク検証で確認）。

### REQ-V2-02: 別会話への文脈混入防止（会話スコープの厳格分離）
* **対応WISH**: `WISH-V2-01`, `WISH-V2-02`
* **根拠**: 異なる話題のスレッドの記憶が混ざることで、AIが誤った前提で回答するハルシネーションや情報漏洩（別話題の混入）を防ぐため。
* **要件内容**:
  * メッセージの保存および文脈抽出クエリは、必ず対象となる一意の `conversation_id` でフィルタリング（`WHERE conversation_id = $1`）を行う。
  * フロントエンドで会話を切り替えた際、メモリ上の表示状態および送信先の `conversation_id` を即座に切り替え、前の会話のDOMや文脈配列を残存させない。
* **受入条件（操作判定）**:
  1. 会話Aで「私の好きな果物はリンゴです」と発言した後、新規作成した会話Bに切り替えて「私の好きな果物は何ですか？」と質問した際、会話Aの「リンゴ」という情報を参照せず「分かりません」等の回答が返ること。

### REQ-V2-03: 新規会話スレッドの作成
* **対応WISH**: `WISH-V2-02`
* **根拠**: 話題が変わった際に、利用者がワンクリックで真っ白な状態の新しい対話空間を開始できるようにするため。
* **要件内容**:
  * 画面上に「新しい会話」ボタンを配置する。
  * ボタンを押下すると新しい会話スレッドが作成（または新規スレッド状態へ遷移し初回送信時にDBへ登録）され、メッセージ表示エリアが空の初期状態になる。
  * 会話一覧の先頭に新しい会話が追加され、自動的に選択状態（アクティブ）となる。
* **受入条件（操作判定）**:
  1. 既存の会話を開いている状態で「新しい会話」ボタンを押下すると、画面中央のメッセージ履歴表示が0件（初期状態）に切り替わること。
  2. そのまま質問を送信すると、既存の会話には追加されず、新しい会話スレッドの1往復目として保存・表示されること。

### REQ-V2-04: 会話一覧の表示と切り替え（画面表示最大20往復）
* **対応WISH**: `WISH-V2-02`
* **根拠**: 複数の話題を並行して進められるよう、過去の会話スレッドを一覧から視認・選択し、対話の流れを振り返れるようにするため。
* **要件内容**:
  * 画面のサイドバーまたは一覧領域に、保存済みの会話スレッドを更新日時（または作成日時）の新しい順に表示する。各項目には会話タイトル（初回質問の先頭20〜30文字等）と日時を表示する。
  * 一覧から任意の会話を選択すると、当該会話に紐づくメッセージ履歴を**最新最大20往復（40メッセージ）**取得し、会話の流れが追える時系列順（上から下へ古い→新しい順）で画面に描画する。
* **受入条件（操作判定）**:
  1. 複数の会話（会話A、会話B）を作成した後、一覧から会話Aをクリックすると会話Aのやり取りが表示され、会話Bをクリックすると会話Bのやり取りに切り替わること。
  2. 1つの会話に25往復の履歴がある場合、画面には直近20往復分が表示されること。

### REQ-V2-05: 再読み込み後の会話選択と再開
* **対応WISH**: `WISH-V2-03`
* **根拠**: ブラウザのリロード（F5）やタブを閉じて再度開いた後でも、作業中の対話を途中から継続できるようにするため。
* **要件内容**:
  * 会話スレッドおよびメッセージ履歴はすべて PostgreSQL データベースに永続化する。
  * ページ再読み込み時、バックエンドから保存済みの会話一覧を取得して描画する。利用者が一覧から任意の会話を選択することで、過去の履歴（最大20往復）が復元され、そのまま追加質問（直近5往復文脈付き）を送信して再開できる。
* **受入条件（操作判定）**:
  1. 会話Aで2往復のやり取りを行った後、ブラウザの再読み込み（リロード）を実行する。
  2. 再読み込み後の画面の会話一覧に会話Aが存在し、それを選択すると2往復分の履歴が復元表示されること。
  3. 復元された会話Aに対して3往復目の追加質問を送信すると、1〜2往復目の文脈を踏まえた回答が返り、DBに追記されること。

### REQ-V2-06: 初期状態（0件）と非同期通信中のUI制御
* **対応WISH**: `WISH-V2-02`, `WISH-V2-03`
* **根拠**: **【授業の共通条件】** 通信中の連打による重複リクエスト防止、および初期データ0件時の正常表示を担保するため。
* **要件内容**:
  * データベースに会話が1件も存在しない初期状態では、「保存された会話はありません。新しい質問を入力して開始してください。」等の正常な0件案内を表示し、エラー扱いにしない。
  * 履歴取得中およびAI回答生成中（送信中）は、送信ボタンおよび入力欄を非活性（`disabled` / `aria-busy="true"`）にし、通信完了後（成功・失敗問わず `finally` 節）に必ず操作可能状態へ復帰させる。
  * 入力値・AI回答・会話タイトルのDOM描画には `textContent` のみを使用し、`innerHTML` への直接代入を禁止する（XSS対策）。
* **受入条件（操作判定）**:
  1. DBの会話データが0件の状態で `/ai` にアクセスした際、エラー表示が出ず正常に新規質問を送信できること。
  2. 質問送信ボタン押下後、回答が返るまでの間は送信ボタンが押下不可（`disabled`）になり、完了後に再び押下可能になること。
  3. `<script>alert(1)</script>` を含む質問を送信してもスクリプトが実行されず文字列として表示されること。

### REQ-V2-07: 送信失敗・異常系の安全なハンドリング
* **対応WISH**: `WISH-V2-01`, `WISH-V2-03`
* **根拠**: **【授業の共通条件】** 外部API障害やタイムアウト発生時に、入力データの消失やサーバークラッシュを防ぐため。
* **要件内容**:
  * 入力バリデーション（前後空白トリム後、1〜2,000コードポイント以内）に違反した場合は通信を行わずエラーメッセージを表示する。
  * Gemini API のタイムアウト（サーバー側30秒 / フロント側45秒）、APIキー不正、ネットワーク切断、不正JSON応答が発生した場合、画面に安全なエラー案内を表示する。
  * **失敗時のデータ整合性**: AI応答の生成に失敗した場合、ユーザー入力欄のテキストは消去せず保持し、不完全な片側メッセージ（回答なしの質問だけ等）が会話文脈を壊さないよう制御する。
* **受入条件（操作判定）**:
  1. 空文字または2,001文字以上の入力で送信した際、API通信が発生せず警告メッセージが表示されること。
  2. サーバー側タイムアウトまたはAPIエラー発生時、入力欄の文字が消えずに残っており、エラー表示後に再送信操作が可能であること。

## 5. データ要件

### 5.1 データモデル概要（PostgreSQL）
V2では「会話スレッド」と「会話内の各メッセージ（または往復ログ）」を 1対多（`1 : N`）で管理する。

1. **会話テーブル (`ai_conversations`)**
   * `id`: 主キー（連番 `BIGINT GENERATED ALWAYS AS IDENTITY` または UUID）
   * `title`: 会話タイトル（`VARCHAR` / `TEXT`、初回質問の抜粋等を自動設定）
   * `created_at`: 作成日時（`TIMESTAMPTZ NOT NULL DEFAULT NOW()`）
   * `updated_at`: 最終更新日時（`TIMESTAMPTZ NOT NULL DEFAULT NOW()`、一覧の並び順に使用）
2. **会話メッセージテーブル (`ai_conversation_messages` または `ai_qa_logs` 拡張)**
   * `id`: 主キー（`BIGINT GENERATED ALWAYS AS IDENTITY`）
   * `conversation_id`: 外部キー（`ai_conversations.id` を参照、`ON DELETE CASCADE`）
   * `role`: 発言者区分（`'user'` または `'model'` / `'assistant'`）※または1レコード1往復構造（`prompt`, `response_text`）に `conversation_id` を紐付ける形式
   * `content`（または `prompt` / `response_text`）: 発言テキスト（`TEXT NOT NULL`）
   * `created_at`: 作成日時（`TIMESTAMPTZ NOT NULL DEFAULT NOW()`）

### 5.2 件数上限・保持ルール
* **会話一覧取得上限**: 最新20〜50件（更新日時降順）。
* **画面描画メッセージ上限**: 選択された1会話につき**直近20往復（40メッセージ）**。
* **AI文脈送信上限**: 選択された1会話につき**直近5往復（10メッセージ）**＋今回の質問1件。
* **SQLインジェクション対策**: すべてのDBクエリはプレースホルダ（`$1, $2...`）を用いたパラメータ化クエリで実装する。

## 6. 運用・非機能要件（授業共通条件）

### REQ-V2-08: V1および既存機能（TOP / TODO）への非干渉
* **根拠**: **【授業の共通条件】** 既存の稼働中機能およびV1の提出成果物を破壊しないこと。
* **要件内容**:
  * 既存のTOPページ（`GET /`）、DBヘルスチェック（`GET /api/db-check`）、TODOアプリ（`/todo` および `/api/v1/todos`）のルーティング・DBテーブル・動作に影響を与えないこと。
  * V1で使用していた `ai_qa_logs` テーブルおよび V1 API（`POST /api/ai/ask`, `GET /api/ai/history`）は互換性を維持するか、V2専用のエンドポイント（例: `/api/ai/v2/...` または後方互換パラメータ）として分離し、V1の単体動作が損なわれないようにする。
* **受入条件（操作判定）**:
  1. V2実装後に `/` と `/todo` にアクセスし、TODOの追加・完了・削除が従来通り正常に動作すること。
  2. V1のテストシナリオ（単発質問・履歴取得）がエラーなく通過すること。

### REQ-V2-09: 公開時（本番・評価環境）の安全な機能停止ガード
* **根拠**: **【授業の共通条件】** APIキー未設定の公開環境（Preview/Production）において、サーバーエラー（500）やクラッシュを起こさず安全に機能を停止させるため。
* **要件内容**:
  * 環境変数 `GEMINI_API_KEY` が未設定または空文字の場合、V2の画面表示およびすべてのV2 APIエンドポイントは外部APIやDBへの無駄なアクセスを行わず、即座に **HTTP `503 Service Unavailable`**（および「現在AI機能は停止中です」の案内）を返却する。
  * APIキー等の秘密情報はソースコードやフロントエンドJSに一切ハードコードせず、`.env`（Git管理除外）経由でのみ読み込む。
* **受入条件（操作判定）**:
  1. `.env` から `GEMINI_API_KEY` を削除してサーバーを起動し、V2画面およびV2 APIへアクセスした際、サーバーが落ちずに HTTP 503 と停止案内が返ること。

### REQ-V2-10: パフォーマンス・タイムアウト・リクエスト制限
* **根拠**: **【授業の共通条件】** 外部API遅延によるサーバーリソース枯渇および過大ペイロード攻撃を防止するため。
* **要件内容**:
  * リクエストボディサイズの上限を `10kb`（または文脈を含めた妥当な上限値）に制限する。
  * Gemini API 呼び出しには `AbortController` による **30秒タイムアウト** を設定し、SDK/fetch の自動リトライは無効（0回）とする。
